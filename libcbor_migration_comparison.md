## 2. Deep Dive: Analysis of Failure Modes

The regression suite of 198 test cases uncovered fundamental differences in how each compiler model translated the legacy C code.

### A. Old Parser Repository (`libcbor_output_5_nano_old_parser`) — 68 Failures

The old parser took a highly simplified procedural approach. Rather than building a full object tree matching C's `cbor_item_t`, it attempted to decode CBOR directly into basic Java primitives (`Long`, `String`, `byte[]`, `List`, `Map`). This shortcut led to severe functional gaps:

1. **Negative Integer Omission (44 Failures):**
   * **Symptom:** All negative integer tests (e.g. `0x20` -> `-1L`, `0x38 0x18` -> `-25L`) returned `null` instead of the negative value.
   * **Root Cause:** Although the parser bóc tách and parsed negative bytes into `NegativeIntToken`, the `CborDecoder.decode()` implementation completely omitted the `instanceof NegativeIntToken` conditional block. The decoded token simply fell through and returned `null`.
2. **Special Types & Floats (5 Failures):**
   * **Symptom:** `testBoolFalse`, `testBoolTrue`, `testNull`, `testDoubleZero`, `testDoubleOne` all returned `null`.
   * **Root Cause:** Similar to negative integers, the control tokens (`BoolToken`, `NullToken`, `FloatToken`) were partially implemented as classes, but the decoder logic fell through without mapping them to native Java equivalents (`Boolean`, `null`, `Double`).
3. **8-Byte Integer Overflow / Narrowing Casts (5 Failures):**
   * **Symptom:** Large 64-bit unsigned integers like `4294967296L` and `4294967297L` decoded to `0` and `1` respectively.
   * **Root Cause:** The parser used standard lossy integer casts (e.g., `(int) len`) or narrowing operations that wrapped large 64-bit offsets.

### B. Version 2 Repository (`version_2/libcbor`) — 17 Failures

The `version_2` repository generated by `gpt-5.4` on Atlas Cloud represents a major architectural leap. It fully maps the C struct `cbor_item_t` to a Java interface `CborItem` and concrete types under the `types` package, preserving C-style refcounting, definite/indefinite width constraints, and metadata structures. It failed only 17 edge cases:

1. **Definite Array Syntax Errors (15 Failures):**
   * **Symptom:** Tests evaluating arrays (e.g., `testArraySize0` to `testArraySize14`) threw `MalformedCborException: cbor_load: Syntax error / Malformed data`.
   * **Root Cause:** The streaming parser state machine (`CborStreamingDecoder`) uses a nested `CborParserContext` with stack-based frames (`ArrayFrame`, `MapFrame`). Definite-length array frames were checking size boundaries in a way that incorrectly triggered EOF or structural validation exceptions when sub-elements were read sequentially, rejecting standard C-style array byte layouts.
2. **Double-Float Decoded as Simple Value (2 Failures):**
   * **Symptom:** Double-precision floats (`testDoubleZero` and `testDoubleOne`) returned `null` because they matched `CborFloatControl.Simple` instead of `CborFloatControl.Double`.
   * **Root Cause:** In `CborLoad.java` or `CborStreamingDecoder.java`, major type 7 decoding checks the additional information (`ai = 27`). The parser mapped it to `CborFloatControl.Simple` due to a minor routing logic oversight in the `ai` switch case block, causing the 64-bit double payload to be treated as a control byte instead of being parsed as IEEE 754 double bits.

## 3. Structural Comparison & Conclusion

The comparison highlights why **Documentation-Guided Translation** is essential for codebase migration:

* **Old Parser (No documentation guidance):** It made lazy assumptions. It skipped generating missing classes like `ByteStringToken.java`, and cut corners by mapping everything directly to native Java structures without implementing C's custom data boundaries (like tag nesting and refcounts). This resulted in an uncompilable and logically broken project.
* **Version 2 (Guided by `IMPLEMENTATION_PLAN.md`):** It designed a full object-oriented model mirroring C structures exactly. By establishing the plan first, it ensured every class was fully implemented, compilation was solid, and the functional logic succeeded in over **91.4%** of the cases, needing only minor adjustments in the parser state machine.
